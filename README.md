# Вариант B — Launch Control: оптимизация образа

Перед вами API управления запусками ракет. Сервис маленький, работает и покрыт тестами. Проблема не в нём, а в том, **как он упакован**.

Текущий образ весит больше гигабуйта, пересобирается несколько минут после правки одной строки кода, тащит в прод компилятор, `vim`, тесты и токен в переменной окружения. При этом он собирается и проходит тесты — то есть «работает», и именно поэтому его три релиза никто не трогал.

Ваша задача: с помощью coding-агента привести упаковку в порядок так, чтобы **улучшение было измеримым, а сервис остался рабочим**.

## Правила игры

1. **Приложение не трогаем.** `app/` и `tests/` менять нельзя. Если считаете, что без правки приложения не обойтись — сделайте и объясните в README, почему.
2. **Правки вносит агент**, вы ставите задачу и принимаете решение. Промпты и ключевые ответы идут в ваш `README.md`.
3. **Каждое улучшение подтверждается замером.** Не «стало лучше», а «было 1420 MB → стало 190 MB».
4. Ничего никуда не пушим: только локальный демон Docker.

## Быстрый старт

```bash
# 0. проверить инструменты и сгенерировать лок-файл
./scripts/tools.sh
uv lock

# 1. снять baseline (это займёт несколько минут — так и задумано)
./scripts/bench.sh baseline

# 2. посмотреть табло
BASELINE_MB=<размер из шага 1> ./scripts/score.sh baseline
```

`bench.sh` меряет четыре величины и дописывает результат в `bench-results.md`. `score.sh` показывает девять проверок, которые к сдаче должны позеленеть.

Ожидаемая картина на старте — примерно такая:

```
  ✗ Размер <= 400 MB                  1423 MB
  ✗ Работает не от root               root
  ✗ Есть HEALTHCHECK
  ✗ Нет компилятора в runtime         найден gcc/cc
  ✗ Нет dev-инструментов              найдено: git vim pytest
  ✗ Тесты не едут в образ             /app/tests существует
  ✗ Нет секретов в ENV                проверьте docker image inspect
  ✗ Есть .dockerignore                файла нет
  ✗ hadolint без ошибок               4 error

  Готово: 0/9
```

Цель — довести до `9/9`, не сломав приложение.

## Четыре метрики

| Метрика | Чем важна |
| --- | --- |
| Размер образа | Скорость выкатки, стоимость хранения и трафика |
| Число слоёв и их вес | Показывает, что лишнего попало внутрь |
| Холодная сборка | Время CI на чистой машине |
| **Тёплая пересборка** | **Сколько ждёт разработчик после правки одной строки** |

Последняя — самая важная и её чаще всего забывают. Она не видна ни в размере образа, ни в `hadolint`: её показывает только замер. Если после правки кода заново ставятся зависимости — порядок слоёв неверный, чем бы ни был занят остальной `Dockerfile`.

`bench.sh` меряет её честно: сам дописывает строку в `app/main.py`, пересобирает, замеряет и откатывает правку.

## Где искать проблемы

Подсказок в виде списка дефектов не будет — их нужно найти инструментами:

```bash
hadolint Dockerfile              # претензии к самому Dockerfile
docker history launch-control:baseline   # что и сколько весит по слоям
dive launch-control:baseline     # efficiency score и wasted space
trivy image launch-control:baseline      # уязвимости и лишние пакеты
docker run --rm --entrypoint sh launch-control:baseline -c 'du -sh /app/* | sort -h'
```

Отдельно посмотрите на список зависимостей в `pyproject.toml` и на то, **какие из них реально импортируются приложением**. Простое `grep -r "^import\|^from" app/` бывает откровением. Не всё, что лежит в `dependencies`, нужно рантайму — и это не про Docker, это про то, что агенты и люди одинаково легко складывают в проект лишнее.

## Что должно получиться

Минимальный набор:

- многоступенчатая сборка: сборочные зависимости в финальный образ не попадают;
- обоснованный выбор базового образа — в README назовите, какие альтернативы отвергли и почему;
- слои разложены под кэш: правка кода не переустанавливает зависимости;
- `.dockerignore`, отсекающий `.git`, окружения, кеши, тесты;
- никаких dev-зависимостей и секретов в финальном образе;
- non-root пользователь;
- зафиксированный базовый образ (тег с версией, лучше — digest);
- `HEALTHCHECK`, который не тянет в образ лишних утилит;
- ваш `scripts/smoke.sh`, который поднимает контейнер, дёргает эндпоинты и **падает с ненулевым кодом**, если что-то не отвечает.

Smoke-тест — ваша ответственность и он обязателен. Образ, похудевший в десять раз и не стартующий, не считается результатом.

## Ориентиры

Цифры зависят от машины и версий, поэтому смотрите на порядок величины:

| | было | цель |
| --- | --- | --- |
| Размер | ~1.4 GB | ≤ 250 MB |
| Тёплая пересборка | минуты | секунды |
| `dive` efficiency | ~60–75% | > 95% |
| HIGH/CRITICAL в `trivy` | десятки | единицы или ноль с объяснением |

Ноль уязвимостей недостижим на большинстве баз — честный список оставшихся с объяснением лучше, чем подогнанный результат.

## Проверка себя перед сдачей

```bash
docker build -t launch-control:optimized .
BASELINE_MB=<размер baseline> ./scripts/score.sh optimized   # ожидается 9/9
./scripts/bench.sh optimized                                 # цифры «после»
./scripts/smoke.sh                                           # ваш скрипт, должен пройти
uv run pytest -q                                             # приложение не сломано
```

## Что сдавать

См. общий список в `task.md` занятия. Коротко: финальный `Dockerfile`, `.dockerignore`, `scripts/smoke.sh`, `bench-results.md` с замерами до/после, и `README.md`, в котором обязательно есть:

- таблица «приём → размер → Δ» с промежуточными сборками (что именно и на сколько повлияло);
- сравнение `hadolint`/`trivy`/`dive` до и после;
- раздел **«Что агент предложил, а я отклонил»** — минимум два случая.

Последний пункт не формальность. Агент почти наверняка предложит что-нибудь, что уменьшит образ и сломает его работу. Если вы не нашли ни одного такого предложения — скорее всего, вы не проверяли, а верили.
